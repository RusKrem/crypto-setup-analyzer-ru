# PATCH 14: Безопасность доставки Telegram

## Что изменено

- Перед каждым сетевым вызовом Bridge атомарно сохраняет `delivery_state="sending"`.
- После подтверждённого ответа Bot API сохраняются `telegram_sent=true`, `delivery_state="sent"`, ответ API и время отправки.
- Явные отказы Telegram (ответ API `ok=false` и HTTP 4xx) остаются в обычном retry с backoff.
- Ошибки DNS и явный `ConnectionRefusedError`, доказывающие, что запрос не был отправлен, также остаются в retry.
- Timeout, разрыв соединения, ошибка чтения/декодирования ответа и HTTP 5xx считаются неоднозначным исходом. Автоматическая повторная отправка запрещена.
- Неоднозначные события получают `delivery_state="delivery_unknown"` и перемещаются в `telegram_queue/failed/delivery_unknown/` для ручной сверки.
- Если Bridge перезапустился и обнаружил событие со статусом `sending`, оно также переводится в `delivery_unknown`, а не отправляется повторно.
- Уже подтверждённые события продолжают только локальную архивацию Observer.
- Добавлена межпроцессная блокировка: Windows использует `msvcrt.locking`, POSIX использует `fcntl.flock`. ОС освобождает блокировку при завершении процесса.

## Важное ограничение

Telegram Bot API не предоставляет idempotency key для `sendMessage`/`sendPhoto`. Поэтому невозможно гарантировать exactly-once доставку. Новый режим выбирает осторожную семантику: при неопределённом исходе сообщение не отправляется автоматически повторно, чтобы не создавать дубликаты. Это может потребовать ручной проверки канала и восстановления события.

Файлы в `failed/delivery_unknown` не обрабатываются автоматически. После проверки фактической доставки оператор может удалить файл, либо вернуть его в активную очередь с `delivery_state="pending"` и удалить `telegram_sent`, `telegram_result`, `sent_ts` только если подтверждено, что Telegram сообщение не принял.

## Совместимость

Старые JSON-файлы без `delivery_state` трактуются как `pending`. Старые файлы с `telegram_sent=true` продолжают архивироваться как доставленные. Торговые условия, фильтры сигналов и формат данных сканера не менялись.

## Проверки

Добавлены тесты на timeout после начала запроса, восстановление после перезапуска со статусом `sending`, явный отказ API, HTTP 4xx и блокировку второго экземпляра Bridge. Результат CI фиксируется отдельно после выполнения workflow.
